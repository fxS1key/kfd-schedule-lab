# Объяснение выбора типов и архитектуры
- Использование sealed class позволяет компилятору гарантировать обработку всех возможных состояний парсинга (when) и команд без необходимости использования общих веток else.
- Для конкретных типов занятий (Lecture, Practice, Exam, Cancelled) выбраны data class. Они предоставляют удобные методы сравнения (equals/hashCode), строковое представление (toString) и распаковку.
# НО!!!
Встроенный copy() у data class повторно вызывает конструктор, но при копировании мог передавать исходный изменяемый список преподавателей, что приводило к рассогласованию данных и нарушению инвариантов модели.

Для устранения проблемы реализован метод customCopy(), который создаёт независимую копию списка преподавателей и повторно запускает валидацию через конструктор. При этом встроенный copy() остаётся без изменений.

# Защита коллекций
- Репозитории предоставляют неизменяемые объекты (List вместо MutableList) или возвращают защитные копии (fooList.toList()) внутренних коллекций для предотвращения несанкционированного изменения извне и поддержания инкапсуляции.

# Поведение делегирования
- Интерфейс SessionRepository содержит метод addAll(sessions: List<Session>). Если переопределить в обертке исключительно add, то пакетное добавление через addAll выполнится напрямую через базовый делегат в обход логики аудита. В результате счетчик операций и журнал событий не зафиксируют пакетные добавления, что нарушит требования к целостности логов. Для корректной работы необходимо явно переопределять оба метода (add и addAll), либо гарантировать, что addAll внутри делегата не вызывает атомарный add поштучно (или наоборот, перехватывать вызовы правильно, учитывая правила подсчета событий без дублирования).
